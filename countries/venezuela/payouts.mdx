## Overview

Create a payout from an operative **USDT** account with `POST /api/v1/ve/transactions/outbound`. Check the recipient first with `POST /api/v1/ve/recipients/kyc` when you want the verification result before you reserve funds.

`amount` is a positive USDT decimal string. Do not send a JSON number. A request `amount` with more than 8 fractional digits is rounded down to 8 and is not rejected for the extra digits. If that rounded value is not greater than zero, both cash-in and payout create return `400` with `{ error: "Validation failed", details: [{ field: "amount", message: "Amount must be positive" }] }`. VES fields are metadata only.

Bank, account-type, and document-type values come from `GET /api/v1/ve/banks`. This guide does not list them.

## Prerequisites

- Bearer API token that can pay from the USDT account
- Catalogue values from `GET /api/v1/ve/banks`

## Banks

`GET /api/v1/ve/banks` returns `country` and `onramp`.

`country` includes `pais`, `nombre`, `moneda`, `banks`, `accountTypes`, `documentTypes`, and `phoneCode`. Each catalogue item is `{value, label}`.

`onramp.banks` items are `{id, name}`. Use `name` as `bancoPago` on cash-in. Do not send that name as payout `banco`.

If the payment integration is not configured, the API returns `500` with `code: VE_BANKS_PROVIDER_NOT_CONFIGURED`. A bank-list fetch failure returns `502` with `code: VE_BANKS_PROVIDER_ERROR`. Those bank-catalogue responses include `error`, `code`, and `type`.

Send payout `banco`, `tipoCuenta`, and `tipoDocumento` as the catalogue `value` from `country.banks`, `country.accountTypes`, and `country.documentTypes`. String labels are accepted for compatibility.

`BANK_VALUE` and `ACCOUNT_TYPE_VALUE` in the examples below are placeholders. Replace them with values from `GET /api/v1/ve/banks`.

## Recipient check

`POST /api/v1/ve/recipients/kyc` checks a recipient before a payout. It does not create a transaction, does not reserve USDT, and does not save a bank account. An email that is not registered is not registered by this call.

Required: `accountId` (an operative USDT account you can pay from), `email`, `documentoIdentidad`, `tipoDocumento`.

Optional: `numeroCuenta`. When you send it, `ready` means identity verification is approved and that account is already on file. When you omit it, `ready` means approved and a bank account is already on file. When you send `numeroCuenta`, `kyc_approved_no_account` means verification is approved and that account number is not on file. When you omit `numeroCuenta`, it means verification is approved and no bank account is on file.

`documentoIdentidad` is digits only. The letter belongs in `tipoDocumento` (`V`, `J`, `P`, or `E` from the banks catalogue). A matching `V-`, `J-`, `P-`, or `E-` prefix is accepted and stripped.

A missing account returns `404`. If you cannot pay from that account, or it is not a Venezuela USDT account, the API returns `403`. A non-operative account returns `403` with `code: ACCOUNT_NOT_OPERATIVE`. **`Restringida`** returns `403` with `code: RESTRICTED`.

`firstName`, `lastName`, `prefijoTelefono`, `numeroTelefono`, `direccion`, and `ciudad` are required only when the email is not already registered (`400`, `code: VE_RECIPIENT_DETAILS_REQUIRED`). When those fields are present and the email is still not registered, the response is `kyc_not_started` without `kyc_url`.

A document that does not match that email returns `400` with `code: VE_IDENTITY_UNCONFIRMED` and does not start verification.

Success `status` is `ready`, `kyc_approved_no_account`, `kyc_in_progress`, `kyc_not_started`, or `kyc_declined`.

`kyc_declined` includes `code: VE_KYC_DECLINED`. For an email that is already registered and has no session, this call can start verification and return `kyc_url`. For an existing recipient, `kyc_not_started` returns `kyc_url` when a session URL was issued. `kyc_in_progress` includes `kyc_url` only when the status payload has one, or when a payout on this `accountId` already stored one. Do not read that URL from another account's transactions.

```bash
curl -X POST https://hg.cash/api/v1/ve/recipients/kyc \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "accountId": "YOUR_ACCOUNT_UUID",
    "email": "payer@example.com",
    "documentoIdentidad": "00000000",
    "tipoDocumento": "V"
  }'
```

## Create a payout

Required: `accountId`, `amount`, `firstName`, `lastName`, `email`, `documentoIdentidad`, `tipoDocumento`, `prefijoTelefono`, `numeroTelefono`, `direccion`, `ciudad`, `pais` (`"VE"`), `banco`, `tipoCuenta`, `numeroCuenta`, `nombreTitular`, `apellidoTitular`.

Optional: `celular`, `webhookUrl`. `celular` is required when `tipoCuenta` is Pago Móvil (`13`, `"Pago Móvil"`, or `pago_movil`). Use `+580000000000` only as a placeholder phone.

A missing or invalid bearer token is `401`. Any other validation failure is `400` with `{ error: "Validation failed", details: [{ field, message }] }`.

Available USDT is the ledger minus other outbound rows in `processing` or `pending_kyc` and the outbound fees on those rows. This payout's amount plus its own outbound fee must fit in what remains. If it does not, the response is `409` with `{ error, code }` only and `code: INSUFFICIENT_NET_BALANCE`. No payout row is inserted. `details` is not returned.

If the recipient still needs identity verification, the response is `201` with `status: pending_kyc`, `kyc_url` when a URL was stored, and `kyc_expires_at` (24 hours from create). That amount and its outbound fee stay reserved. The account balance is not debited. No payout order is created until verification is approved.

Approved verification with a usable bank account returns `201` with `status: processing`. When a `processing` row was already inserted and payout dispatch could not be enqueued, the response is `500` with `{ error: "Failed to enqueue outbound processing" }`. The row stays `processing`. A `pending_kyc` create does not enqueue and does not use this response.

Declined verification, verification that finished without approval, an email whose document does not match, a rejected document, or a rejected bank account does not create a transaction and returns `400`:

| `code` | Result |
| --- | --- |
| `VE_KYC_DECLINED` | Verification was declined |
| `VE_KYC_NOT_APPROVED` | Verification finished without approval |
| `VE_IDENTITY_UNCONFIRMED` | The document does not match the email |
| `VE_INVALID_DOCUMENT` | The document was rejected. Send digits only. The letter belongs in `tipoDocumento` |
| `VE_INVALID_BANK` | The bank account was rejected |
| `missing_cuenta_id` | The payout account could not be saved. Check `numeroCuenta` and retry |
| `missing_terms` | The recipient could not be prepared. Retry shortly |

The `error` string says what to fix for a bank-account or document failure.

```bash
curl -X POST https://hg.cash/api/v1/ve/transactions/outbound \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "accountId": "YOUR_ACCOUNT_UUID",
    "amount": "25.5",
    "firstName": "Ada",
    "lastName": "Example",
    "email": "payer@example.com",
    "documentoIdentidad": "00000000",
    "tipoDocumento": "V",
    "prefijoTelefono": "+58",
    "numeroTelefono": "0000000000",
    "direccion": "Example street",
    "ciudad": "Example city",
    "pais": "VE",
    "banco": "BANK_VALUE",
    "tipoCuenta": "ACCOUNT_TYPE_VALUE",
    "numeroCuenta": "00000000000000000000",
    "nombreTitular": "Ada",
    "apellidoTitular": "Example",
    "webhookUrl": "https://merchant.example/hooks/hg"
  }'
```

`BANK_VALUE` and `ACCOUNT_TYPE_VALUE` come from `GET /api/v1/ve/banks`. The phone placeholder is `+580000000000` (`+58` and `0000000000`).

## Status

`GET /api/v1/ve/transactions/{id}/status` reads inbound or outbound status. `amount` is a USDT decimal string. `status` includes `pending_kyc`.

The body always includes `id`, `status`, `direction`, `amount`, and `currency`. `externalID` is omitted until the order id exists, then it is returned. Optional fields, only when present:

- `orden_id`, `montoFiat`, `tasaCompra`
- inbound-only `banco` and `numero_cuenta`
- outbound `kyc_url`
- `kyc_expires_at` while a `pending_kyc` hold is open (24 hours from create)
- `feeBreakdown` when a fee snapshot exists. It omits `flatFee.source`

For an outbound cancelled because identity verification was required, `kyc_url` is included only when a non-empty URL was stored. `cancelledReason` is included only for `VE_KYC_EXPIRED`, `VE_KYC_DECLINED`, or `VE_KYC_REQUIRED`. Other cancellation reasons are omitted.

The merchant `status_change` webhook includes `cancelledReason` only for those same three codes. See [Account movement](/api-reference/webhooks/account-movement).

## Account status

The source account must be **`Operativa`** and **USDT**. **`Bloqueada`** or **`Cerrada`** returns `403` with `code: ACCOUNT_NOT_OPERATIVE`. **`Restringida`** returns `403` with `code: RESTRICTED`. A missing account returns `404`. No access returns `403`. `POST /api/v1/ve/transactions/outbound` returns `400` for an unsupported account or a non-USDT currency.
