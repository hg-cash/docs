## What gets delivered

HG.Cash enqueues an asynchronous **`POST`** to:

1. Your user’s **default webhook URL** (configured in HG.Cash **Settings** alongside the webhook signing secret), **or**
2. A **`webhookUrl`** you pass **per operation** where the API or form allows it — for example creating a ledger transaction via the REST API (`POST /api/v1/transactions`) or a **transaction request** from the transfers flow when that field is available.

Payloads are identical in shape regardless of queue: **`Content-Type: application/json`**. Every payload includes **`topic`** and **`eventType`** at the top level for routing. Most webhook bodies are a single flat JSON object; **`checkout.completed`** may additionally include a nested **`transaction`** object with ledger movement details (same fields as [**Account movement**](/api-reference/webhooks/account-movement), without `topic` or `eventType`).

## Topic and eventType

| `topic` | `eventType` | When |
| --- | --- | --- |
| `TRANSACTION_REQUEST` | `status_change` | Transaction request status update |
| `TRANSACTION_REQUEST` | `transaction_associated` | Outbound request linked to a ledger transaction (`transactionId` present) |
| `TRANSACTION` | `created` | New account movement persisted |
| `TRANSACTION` | `status_change` | Existing movement status updated |
| `CHECKOUT` | `checkout.completed`, `checkout.awaiting_manual_review`, `checkout.rejected` | Hosted checkout lifecycle |
| `CLAIM` | `status_change` | Claim status changed by an admin update or COELSA auto-reconcile |

Transaction request webhooks always use **`topic` `TRANSACTION_REQUEST`**. When a cash-out is linked to its bank movement, look for **`eventType` `transaction_associated`** (not a separate topic).

**Payload shape and examples** live in the **API reference** (open the **API reference** tab, then **Webhooks**):

- **Transaction requests** (cash-out pipeline, `type` is always **`"request"`**): [**Transaction Request Status Updated**](/api-reference/webhooks/transaction-request-status-updated) — schema **`TransactionRequestStatusWebhook`** with a full example payload.
- **Transaction request linked to ledger row** (after Urbana associates the cash-out with the bank movement): [**Transaction request associated**](/api-reference/webhooks/transaction-request-associated) — same schema with required **`transactionId`**, **`topic` `TRANSACTION_REQUEST`**, and **`eventType` `transaction_associated`**. You may receive this in addition to a status update when the link is established.
- **Ledger / account movements** (money in or out of your HG.Cash accounts; `type` is your movement / transaction type name such as `inbound` or `outbound`): [**Account movement**](/api-reference/webhooks/account-movement) — schema **`AccountMovementWebhook`** with example payloads. When a fee snapshot was stored, the body includes optional **`feeBreakdown`**. See [**Fee breakdown**](#fee-breakdown). When a Brazil PIX movement stores an end-to-end id, the body includes optional **`endToEndId`**. See [**PIX end-to-end id**](#pix-end-to-end-id).
- **Hosted checkouts** (`event` such as `checkout.completed`): [**Checkout events**](/api-reference/webhooks/checkout-completed) — schema **`WebhookCheckoutPayload`**. On **`checkout.completed`**, when a ledger transaction is linked, the payload includes a nested **`transaction`** object (same fields as [**Account movement**](/api-reference/webhooks/account-movement), without `topic` or `eventType`). See **[Hosted checkout](/developers/checkout)** for flows by country.
- **Claim status changes** (`topic` `CLAIM`, `eventType` `status_change`): [**Claim status updated**](/api-reference/webhooks/claim-status-updated) — schema **`ClaimStatusWebhook`**. Sent to your **default webhook URL** when a claim is updated by an admin or auto-reconciled by COELSA. The body matches the **Get claim** (`GET /claims/{id}`) response (without `fileUrl`) plus routing metadata, with an optional **`comment`** field. Webhooks are **not** sent on claim create or comment-only updates. See **[Claims](/claims/introduction)** for the full flow.

**Transaction requests (`type: "request"`)**

Callbacks are sent when HG.Cash **updates** a transaction request’s status or when a request is **cancelled**. When an outbound request is **linked** to its ledger transaction, HG.Cash may send [**Transaction request associated**](/api-reference/webhooks/transaction-request-associated) with **`topic` `TRANSACTION_REQUEST`**, **`eventType` `transaction_associated`**, and the **`transactionId`** of the bank movement row. You may **not** receive a webhook as soon as a request is created while it is only **`PENDING`**; integrate defensively against **ordering** and **duplicates**.

**Ledger transactions**

When a ledger **transaction row** is ingested from webhooks/API and your resolved URL applies, HG.Cash can notify immediately after persistence; `type` is the **business type name**, not `"request"`.

## Fee breakdown

Account movement webhooks (`topic` **`TRANSACTION`**, `eventType` **`created`** or **`status_change`**) include optional **`feeBreakdown`** when HG.Cash stored a fee snapshot on the movement. The field is omitted when there is no breakdown. Internal fee rows do not send a webhook.

Amounts and rates are decimal strings. A rate of **`0.01`** is 1%. **`collectedAmount`** is the percentage charged to you plus one flat fee per transaction. **`platformFee`** is the recorded wallet cost and is not added to **`collectedAmount`**. Webhooks send **`flatFee.amount`** only. They do not include **`flatFee.source`**.

On **`checkout.completed`**, the nested **`transaction`** object uses the same fields, including **`feeBreakdown`** when the linked movement has a snapshot.

```json
{
  "feeBreakdown": {
    "platformFee": { "amount": "60", "rate": "0.005" },
    "transactionFee": { "amount": "120", "rate": "0.01" },
    "flatFee": { "amount": "15" },
    "collectedAmount": "135"
  }
}
```

In this example the movement amount is **12,000**. The client percentage is **1%** (`120`) plus a flat fee of **15**, so **`collectedAmount`** is **135**. The platform percentage (**0.5%**, `60`) is recorded separately.

`GET /api/v1/{br,cl,co,ve,bo}/transactions/{id}/status` returns the same snapshot when one is stored, and includes **`flatFee.source`** (`account` or `platform`). `GET /transaction/{id}/status` is a transaction-request status and does not include **`feeBreakdown`**.

## PIX end-to-end id

Account movement webhooks (`topic` **`TRANSACTION`**, `eventType` **`created`** or **`status_change`**) include optional **`endToEndId`** when the movement stores a Brazil PIX end-to-end identifier. The value is that stored string with surrounding spaces removed. HG.Cash omits the field when the identifier is absent or empty. The field is a top-level property of the JSON body, next to fields such as **`id`** and **`status`**. It applies to inbound and outbound PIX.

You receive it in these cases:

- A PIX status update posts **`eventType` `status_change`** and the identifier is already stored.
- A later provider update stores the identifier for the first time and that update did not already notify you. HG.Cash then sends one **`TRANSACTION` / `status_change`** with the updated body.
- A dashboard resend posts **`eventType` `created`** from the stored movement, and the identifier is already saved.

A status change in the same update includes **`endToEndId`** once. An identifier that is already stored does not trigger another delivery by itself.

On **`checkout.completed`**, the nested **`transaction`** object uses the same movement fields, including **`endToEndId`** when the linked movement has one.

```json
{
  "topic": "TRANSACTION",
  "eventType": "status_change",
  "id": "040eac5b-a998-4879-9d8a-05fd2a08c625",
  "externalID": "bankizi-tx-01",
  "amount": "250.00",
  "currency": "BRL",
  "direction": "Inbound",
  "status": "done",
  "type": "inbound",
  "accountId": "843d9d8b-6db8-47a2-8c22-23b198e99c15",
  "date": "2026-05-02T21:40:00",
  "timezone": "America/Sao_Paulo",
  "endToEndId": "E60701190202505022140DY5DH1K8FL1"
}
```

## Signing secret (`X-HG-Webhook-Signature`)

If your HG.Cash profile has a **webhook signing secret** set, HG.Cash signs the **exact raw JSON body**:

- Algorithm: **`HMAC-SHA256`** over the UTF-8 bytes of the body string HG.Cash will send (`JSON.stringify` equivalent of the payload object).
- Header: **`X-HG-Webhook-Signature`**.
- Format: **`sha256=<hex>`** where `<hex>` is lowercase hex (64 chars).

Verification steps on your server:

1. Read the raw request body **as delivered** — do **not** re-serialize parsed JSON unless you replicate every key order/spacing HG.Cash used.
2. Compute `hex = HMAC_SHA256(secret, rawBody_utf8)` and compare securely to header value after stripping the optional **`sha256=`** prefix (case insensitive).
3. Reject mismatches (**`401`/`403`** on your side is fine).

If no secret is configured in HG.Cash, the **`X-HG-Webhook-Signature`** header **omitted** entirely.

## Retries

Failed deliveries (non-**`2xx`** HTTP status, network errors, or timeouts) are **retried** automatically with this policy:

| Setting | Value |
| --- | --- |
| Max attempts | **4** (includes the first try) |
| Backoff factor | **5** |
| Minimum wait between attempts | **500** ms |
| Maximum wait between attempts | **30** s |
| Jitter | **Off** (no randomization) |

Each attempt is allowed up to **30** seconds of total run time before the delivery job is treated as failed for that attempt.

## Operational expectations

- Respond with **`2xx`** quickly so the delivery counts as successful; otherwise you may receive **repeat** `POST`s until attempts are exhausted or one succeeds.
- Prefer **idempotent** handlers keyed by HG.Cash `id` and `status` transitions you care about — redeliveries or duplicate emits are possible alongside provider quirks.

## Dashboard tools

HG.Cash also records each delivery attempt in the dashboard (transactions and transfers → **Webhooks**) and can **disable** your webhook automatically if failures persist. See **[Delivery history and health monitoring](/developers/webhook-delivery-and-monitoring)** for delivery logs, manual retry, and email alerts.
